# 数据工程笔记：从本项目的 parquet 缓存到 PB 级数据管道

用途：先读懂第 1 节本项目缓存的真实做法作为锚点，然后按第 9 节的顺序学习通用技术点，每节都标了**关键点**，学完回到第 10 节把知识和本项目接上。对应的是数据方向 JD 里「PB 级数据、上千维度、数仓建设、完整性一致性准确性」那一整套话术背后的技术。

## 1. 本项目的缓存是怎么做的（真实锚点）

设计就一句话：**把全管道最贵的一步（Alpha158 特征提取）物化成 parquet 文件，之后所有人只读文件，谁都不再碰提取器**。

真实数字（csi300）：

| 缓存文件 | 形状 | 磁盘占用 |
|---|---|---|
| train.parquet | 656,260 行 × 159 列（158 特征 + 1 标签），2188 个交易日、623 只股票 | 377MB |
| valid.parquet | 145,500 行 × 159 列 | 102MB |
| test_feat.parquet | 257,809 行 × 158 列 | 180MB |
| label_test.parquet | 327,938 行 × 1 列 | 1.7MB |

四个具体机制，每条都对应一条生产级原则：

1. **存在即跳过（幂等）**：`prepare_data()` 先检查四个 parquet 是否都在，在就直接 `read_parquet` 返回，不在才初始化 Qlib、跑 Alpha158 handler、`to_parquet` 落盘。同样的输入跑一百遍，产物只生成一次。
2. **只读共享**：缓存生成后，B1/B3/B4/B6/B7/B10/B12 七个实验全部只读，没人再写。共享数据一旦变成只读，并行任务之间就不会互踩。
3. **写隔离**：唯一需要新数据的 B8（中证 500）建自己的 `universe-csi500/_cache`，代码注释里写死「must never touch common/runs/kan/_cache」——共享的只读，自己的自己写。
4. **换口径就换层，原始层不动**：B9 需要不同的归一化方案，它不做的是「改缓存」，做的是：把**未归一化的原始特征**提一次到 `rolling/_raw/`（580MB），归一化用 pandas 重实现，并且先过一道数值门禁——pandas 版和 Qlib 版逐值对比、最大误差 ≤1e-5 才允许开始训练。原始层不可变、下游全部可重建，这就是数仓「贴源层」的思想。

一个值得注意的数据细节：train 段只有 623 只股票却叫中证 300，因为指数成分 2012–2020 间一直在换。**股票池是随时间变的（point-in-time universe）**，做回测必须用当时的成分名单，否则就是幸存者偏差——这是量化数据岗的经典面试题。

**关键点**：缓存的本质 = 把「贵的确定性计算」物化成列存文件 + 用文件存在性做幂等 + 共享只读写隔离。

## 2. 数据规模阶梯：多大算大，大了会死在哪

| 量级 | 单机 pandas | 会遇到什么 | 该上什么 |
|---|---|---|---|
| < 1GB | 随便玩 | 无 | pandas 就够 |
| 1–10GB | 吃紧 | 内存占用是裸数据的数倍 | dtype 瘦身、pyarrow 后端 |
| 10–100GB | 装不下 | MemoryError | 列裁剪、分块、DuckDB、Polars |
| TB–PB | 无解 | 单机 IO 和内存双双爆炸 | 分区 + Spark/Dask + 湖表格式 |

内存是第一约束。PB 级数据**永远不可能整体读进内存**，所以那一整套技术（列存、分区、下推、分布式）全部围绕同一句话：**只碰需要的那一小块**。

**关键点**：列存（少读列）、分区（少读文件）、谓词下推（少读行）是同一个思想的三个面——最小化 IO。

## 3. 文件格式：为什么大家都选 Parquet

CSV 的三宗罪：纯文本体积大 5–10 倍；类型全靠猜（"2023-01-01" 是字符串还是日期）；只能全量读，没法「只要其中两列」。

Parquet = **列存 + 编码 + 压缩 + 统计信息**，四件事各管一摊：

- **列存**：一列一列地存。同列同类型，压缩率天然高；更重要的是查询可以只读需要的列——从 159 列里取 2 列，IO 直接降两个数量级。
- **编码**：低基数列用字典编码（字符串换成整数索引），重复值用 RLE（游程），时间戳/自增 ID 用 delta 编码。编码是无损的，目的是让后面的通用压缩更好压。
- **压缩**：snappy 快、压缩率一般；zstd 又快又高，是现在的默认推荐；gzip 是老古董。
- **统计信息**：每个行组（row group，一般 128MB–1GB 的数据块）记录每列的 min/max。查询带 `date >= '2023-01-01'` 时，看一眼统计就知道这块数据整个跳过——这叫谓词下推，**不读才是最快的读**。

两个容易混的名词：**Parquet 是磁盘上的列存格式，Arrow 是内存中的列存标准**，两者零拷贝互转是 Arrow 存在的意义。`pandas.to_parquet` 背后干活的引擎就是 pyarrow。

**关键点**：`read_parquet(path, columns=["a","b"], filters=[("date",">=","2023-01-01")])` 里的 `columns=` 和 `filters=` 是免费性能，不用白不用——很多「pandas 慢」其实是把全表读进内存再用代码过滤。

## 4. 分区：PB 级的第一板斧

把一张大表按列值拆成目录树：`data/year=2023/month=06/part-0.parquet`。目录结构本身就是索引。

- **分区键怎么选**：选查询里最高频的过滤列（时间几乎永远是答案）；基数别太高（按用户 ID 分区会炸出几亿个目录）也别太低（按「是否有效」分区只有 2 个文件等于没分）；每个叶子文件保持在 128MB–1GB。
- **分区裁剪**：查询带 `year=2023`，引擎直接跳过其他所有目录，连文件名都不列。
- **小文件问题**：分区过细 + 高频小批量写入 = 几百万个 KB 级小文件，文件系统的元数据操作把一切拖死。解法是定期 compaction（小文件合并成大文件）。

本项目的对应物：「train/valid/test 拆成三个文件」就是最朴素的时间分区；659MB 的量还用不上按年分区，但机制是一回事。

**关键点**：分区是文件级裁剪，row group 统计是文件内裁剪，两层叠加才是完整的「最小化 IO」。

## 5. 计算引擎阶梯：pandas 装不下之后

从下往上，每一级都是前一级装不住时的升级：

1. **pandas 瘦身**（1–10GB）：float64 降 float32 省一半（本项目 656k×159 全程 float32 就是这个意识）；字符串列换 category；`df.memory_usage(deep=True)` 先看钱花在哪。
2. **分块**（10GB 级）：`read_csv(chunksize=...)` 或按 row group 迭代 parquet，内存占用常数化；代价是跨块聚合要自己写合并逻辑。
3. **DuckDB**（几十 GB 级，单机分析首选）：进程内 OLAP 数据库，直接对 parquet 文件写 SQL，列裁剪和谓词下推全自动。`duckdb.sql("SELECT date, close FROM 'data/*.parquet' WHERE date >= '2023-01-01'")`，一行都不用改数据。
4. **Polars**（同上，语法替代品）：Rust 内核、多线程、lazy 执行、Arrow 原生；API 与 pandas 不同，但速度和内存占用好一个量级。
5. **Dask**（TB 级起步）：把大数据切成小 partition，每个 partition 还是一个 pandas DataFrame，调度到多核/多机。学习成本最低的「分布式」，上限也最低。
6. **Ray**（TB 级）：通用分布式框架（任务 + actor），ML 训练场景常用。
7. **Spark**（PB 级，行业标准）：JVM 生态的分布式计算引擎，DataFrame API 背后是 Catalyst 优化器；「数仓建设」招聘语境下的默认答案。

选型一句话：**能 DuckDB 不 Spark**。分布式是最后手段，不是简历装点——把单机列存用到极致，比上来就开 Spark 集群便宜且快。

**关键点**：所有引擎的共同内核是 lazy 执行 + 列裁剪 + 谓词下推 + 尽早过滤。换引擎不换思想，面试时能把这句话讲透比背 API 值钱。

## 6. 数仓与湖表：JD 里「数仓建设」对应的实体

- **数仓分层**：ODS（原始贴源层，原样落地不动）→ DWD（明细层，清洗、去重、类型规整）→ DWS（汇总层，按主题聚合）→ ADS（应用层，直接喂报表/模型）。思想与本项目三层同构：`_raw/` 原始不动、`_cache/` 加工产物、`results/` 结论——只是规模放大一万倍。
- **湖表格式**（Delta Lake / Apache Iceberg / Apache Hudi）：往对象存储的一堆 parquet 上加数据库语义——事务（写一半挂了不留脏数据）、schema 演化（加列不改历史）、时间旅行（查昨天十点的表长什么样）、ACID。Iceberg 是当前面试热词，记住它解决**事务、schema、快照**三件事即可。
- **批流一体**：数据生产两条链路——定时批量重算（准、慢）+ 实时流增量（快、难保序），Lambda/Kappa 架构讨论的就是两条链路怎么合。

## 7. 数据质量：完整性、一致性、准确性分别指什么

JD 那三个词各有对应工程动作：

- **完整性**：该到的到了没有——行数对账、主键唯一、空值率阈值、断流检测（今天的数据没落盘要报警）。
- **一致性**：同一个指标在所有地方口径一致；跨源对账（两张表总数对不上就是事故）；**幂等重跑**——同输入跑两遍结果必须一致，否则重跑就是灾难。本项目的缓存存在即跳过、B9 数值门禁，都是幂等和可校验的微缩版。
- **准确性**：值本身对不对——业务规则校验（价格 > 0、涨跌幅在涨跌停内）、异常值检测。本项目的 `common/data/health/` 和 `diagnose_outliers.py` 就是小型数据质量模块，`verify_cn_data.py` 是入库校验。
- **回填与重放**：上游改了历史数据怎么办——答案是原始层不可变 + 下游全部可重算（replay），本项目的缓存体系天然满足：删掉缓存重新跑一遍 `prepare_data()` 就得到全新产物。

工具名词知道即可：Great Expectations（数据断言框架）、dbt test（SQL 层数据测试）。

## 8. 「毫秒级」那半句：在线和离线是两回事

JD 说「毫秒级处理 PB 级数据」，实际指的不是用 Python 在线算 PB 数据（不可能），而是**离线预计算 + 在线点查**：离线把特征/指标算好存进 KV 存储（Redis、RocksDB），线上请求毫秒级读结果。这层叫特征平台（feature platform / online store），它真正的难点是**离线在线一致性**——训练时用的特征值和线上服务时的特征值必须同一口径（training-serving skew），否则模型上线就掉点。

**关键点**：毫秒是存储结构设计出来的，不是计算引擎算出来的。

## 10. 回到本项目：面试怎么把两层接起来

被问「你做过什么数据处理」时的讲法：本项目缓存体系就是生产数据管道四个原则的微缩版——**物化**（贵的确定性计算落盘：Alpha158 只提一次）、**幂等**（文件存在即跳过，重跑安全）、**隔离**（共享缓存只读，B8 写自己的目录）、**可校验**（B9 用 ≤1e-5 数值门禁保证 pandas 重实现与原链路等价）。数字锚点：656k 行 × 159 列 float32、parquet 377MB、三套缓存共约 2.3GB。再被追问「PB 级怎么办」，答第 2 节的阶梯：单机列存 → 分区 + 下推 → DuckDB/Polars → Spark + Iceberg，收尾落在「一切设计围绕最小化 IO」。

## 11. 数据源层：Qlib bin 格式与复权口径

上游数据是 chenditc/investment_data 发布的 Qlib 数据集（846MB，`/data1/wujunxi/kailin/data/qlib_data/cn_data`），结构只有三件套：

```
calendars/day.txt      6470 个交易日（2000-01-04 ~ 2026-09-11），纯文本
instruments/*.txt      股票池名单（all / csi300 / csi500 / csi800 / csi1000 / csiall）
features/<symbol>/     6154 只股票（含北交所），每股 10 个字段
  open/high/low/close/vwap/volume/amount/change/day.bin + factor.day.bin（复权因子）+ adjclose.day.bin
```

**bin 文件格式**（实测 `sh600000/close.day.bin`，26KB）：前 8 字节是 2 个 float32 的索引头（`start=0.0, step=1.0`），其后是 float32 值数组（6469 个）。第 i 个值对应日历里第 `start + i×step` 天。随机访问是 O(1)：读任意区间只需 `seek(8 + 4×起始下标)` 再连续读，不用解析文本、不用解压，还可以直接 mmap——这正是它不用 parquet/CSV 的原因，因为 Qlib 的访问模式是「海量小范围点查」（每股票每字段读一小段），而不是分析型全表扫描。

**instruments 是逐时点成分**：每行是「股票代码 + 生效区间」，同一只股票在 csi300.txt 里可能出现多段（进出指数多次）。这就是为什么 train 段（2012–2020）实际有 623 只股票而池子叫中证 300——**股票池随时间变化，回测必须用当时的成分名单，否则是幸存者偏差**。

**复权口径是后复权**：依据是数据体检报告（`common/data/HEALTH_REPORT.md`）直接以「后复权价格」命名该字段，并且审计时把「复权收益 = 投资者真实收益（含分红再投）」当地面真实；数值形状也吻合（close 从 2000 年的 ≈0.99 单调放大到 2026 年的 6.29，锚点在序列起点）。口径选择上：**收益比值对前复权/后复权等价**（整体乘常数不改变 `close_t/close_{t-1}`），真正算错的是用不复权价格跨除权日；后复权的实质优势是**锚点固定在过去、每次分红不需要重写历史**——前复权每次分红都会重缩放整段历史，导致缓存失效、不同时间下载的数据对不上、破坏 point-in-time 可复现性。

**我们自己的 parquet 缓存的一个局限**：`train.parquet` 整份写成了**一个行组**（1 row group / 656,260 行 / 未压缩 397MB），而 parquet 的行组 min/max 统计正是文件内跳行的依据——单行组意味着 `filters=` 谓词下推在这个文件上只能整文件排除，等于没用上。要利用起来需要按年写多个行组或按年分区。列裁剪仍然有效（159 列全读 0.50s / 420MB 内存，单列 `label_test` 1.7MB 读 0.039s），编码上 `instrument` 字典编码压到 11%、`datetime` 字典+RLE 压到 0.03MB，而 float32 特征列压缩比 ≈0.99（高熵，几乎压不动）。

## 12. Alpha158 因子计算量实测

执行模型的层次（源码：`qlib/data/data.py::LocalDatasetProvider`、`qlib/data/ops.py::Rolling`）：

- **股票是真实 Python 循环**：`for inst in instruments_d` → 每股调 `ExpressionD.expression(inst, field, ...)` 求值；这个粒度同时是并行单位（预热表达式缓存时用 joblib 按股票分发）。
- **时间不是循环，是数组轴**：每个算子拿到该股该字段的整条时间序列数组，一次运算输出整条结果数组；逐元素算子走 numpy，滚动算子（`Rolling._load_internal` 调 `series.rolling(N).std()` 之类）跑在 pandas/Cython 的编译内核里（滑动窗口 + 增量更新），没有逐日的解释器循环。滚动算子要算区间第一天的值需回看 N−1 天，Qlib 用「最长回看窗口」机制自动补齐。
- **表达式不是 158 次独立计算**：158 个特征展开后只有 **348 个唯一子表达式节点**，原始字段读取只有 **6 个**（`$close/$high/$low/$open/$volume/$vwap`）。实测 `Ref($close,1)` 被 35 个特征引用却只算一次，`MAX($high,5)` 同时服务 `MAX5` 与 `RSV5`。
- **截面算子最后做**：`RANK5..60` 是当日跨股票的秩、标签的 `CSZScoreNorm` 是逐日截面 z-score，这两类必须先拼成 `(datetime, instrument)` 面板，再按日期 groupby 在组内算。

**去重收益按类别拆开**（避免只看总数产生误导）：

| 类别 | 朴素（各特征独立） | 去重后 | 节省 |
|---|---|---|---|
| 字段读取（读一整条序列） | 445（`$close` 被重复读 252 次） | 6 | 99% |
| 逐元素算术 | 458 | 205 | 55% |
| 窗口算子（按窗口扫整条时间轴） | 320 | **137** | 57% |
| 合计 | 1223 | 348 | 72% |

**每特征节点数**：中位数 5、均值 7.7、最小 2、最大 21；96/158 个特征不超过 5 个节点（`MA5 = Mean($close,5)` 只有 2 个），重尾是 `SUMD/SUMN/VSUMD/VSUMN` 各 5 个窗口共 20 个特征、每个 21 个节点。

**结论**：共享子表达式的价值主要在 **IO 与内存**（省掉 445 次重复读序列），而不是 CPU 时间的数量级缩减——真正贵的是那 137 个窗口算子，它们基本是「25 个算子 × 5 个窗口」的笛卡尔积，无法再省。所以笼统说「省了 72% 计算量」会高估收益，按 FLOP 计的实际节省明显低于此。
